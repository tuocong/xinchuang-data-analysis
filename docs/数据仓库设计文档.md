## 1. 项目概述

### 1.1 系统目标

构建一个**双平台（Gitee + GitHub）信创开源项目**数据采集、清洗、建模、分析、可视化的完整链路，最终以数据大屏的形式呈现信创开源生态的健康度指标（Star 趋势、社区活跃度、技术语言分布、组织对比）。

### 1.2 数据源

| 平台 | API | 采集方式 | 采集对象 |
|------|-----|---------|---------|
| Gitee | Open API v5 | 组织列表 + 关键词搜索 | 12 个信创组织（openEuler、MindSpore、openGauss、龙蜥、深度、开放麒麟、鲲鹏等） |
| GitHub | REST API v3 | 组织列表 + 关键词搜索 | 20 个国际/云原生组织（PaddlePaddle、KubeEdge、kubernetes、apache 等） |

采集关键词：`xinchuang` / `信创` / `kunpeng` / `ascend` / `harmonyos` / `openHarmony` / `openEuler`。

### 1.3 技术栈

| 层次 | 技术 |
|------|------|
| 数据采集 | Python `requests` + 指数退避重试 |
| 数据清洗 | Pandas（`drop_duplicates` / `fillna` / `groupby`） |
| 数据存储 | MySQL 8.0（InnoDB，utf8mb4） |
| ETL | Python + PyMySQL（原生 SQL） |
| 后端 API | Flask + Flask-CORS（7 个 REST 接口） |
| 前端可视化 | 纯 HTML + ECharts 5（零构建依赖） |

## 2. 总体架构

采用经典数仓**四层分层架构**：ODS（贴源层）→ DWD（明细层）→ DWS（汇总层）→ ADS（应用层）。

```
┌─────────────┐   ┌─────────────┐
│  Gitee API  │   │  GitHub API │         ① 数据源层
└──────┬──────┘   └──────┬──────┘
       │ collector.py    │
       └────────┬────────┘
                ▼
       ┌───────────────────┐
       │ data/raw/*.json   │              ② 原始 JSON 落盘
       └────────┬──────────┘
                │ cleaner.py (Pandas)
                ▼
       ┌───────────────────┐
       │ data/cleaned/     │              ③ 清洗后数据
       │ repos_cleaned.json│
       └────────┬──────────┘
                │ ods_loader.py
                ▼
   ┌─────────────────────────────────────────┐
   │            MySQL (xinchuang_dw)          │
   │                                           │
   │  ODS   ods_repos_raw          60,963 行   │ ④ 贴源层
   │  ───────────────────────────────────────  │
   │  DWD   dim_project / dim_org / dim_date  │ ⑤ 明细层（星型模型）
   │        fact_repo_stats         48,788 行   │
   │  ───────────────────────────────────────  │
   │  DWS   dws_project/language/org/platform │ ⑥ 汇总层（日粒度 + 增量）
   │  ───────────────────────────────────────  │
   │  ADS   ads_overview/ranking/...   5 张表   │ ⑦ 应用层（对接 API）
   └───────────────┬───────────────────────────┘
                   │ Flask API（7 routes）
                   ▼
       ┌───────────────────────┐
       │  ECharts 数据大屏      │              ⑧ 展示层
       │  14 个前端页面         │
       └───────────────────────┘
```

**分层职责**：

| 层 | 英文 | 职责 | 关键特征 |
|----|------|------|---------|
| ODS | Operational Data Store | 贴源存储，与原始 API 数据 1:1 对应 | 保留完整字段，按 `dt` 日期分区 |
| DWD | Data Warehouse Detail | 明细层，维度建模（星型模型） | 维度表 SCD Type1，事实表日快照 |
| DWS | Data Warehouse Summary | 汇总层，日粒度聚合 + 增量计算 | 含 `LAG` 思想的"两步法"增量 |
| ADS | Application Data Store | 应用层，面向前端的宽表 | 直接供 API 查询，无需复杂 JOIN |

## 3. 分层设计

### 3.1 ODS 层 —— `ods_repos_raw`

贴源表，共 **21 个字段**，与采集器归一化后的 JSON 字段 1:1 对应。

| 字段分类 | 字段名 | 类型 | 说明 |
|----------|--------|------|------|
| 基础标识 | `repo_id` / `org` / `name` / `full_name` / `description` | BIGINT / VARCHAR / TEXT | 仓库基本属性 |
| 核心指标 | `stars_count` / `forks_count` / `watchers_count` / `open_issues_count` | INT | 关键度量 |
| 仓库属性 | `language` / `default_branch` / `html_url` | VARCHAR | 技术标签 |
| GitHub 特有 | `topics` / `license_type` / `homepage` / `archived` | VARCHAR / TINYINT | Gitee 数据填默认值 |
| 时间字段 | `created_at` / `updated_at` / `pushed_at` | VARCHAR(30) | ISO 8601 格式 |
| ETL 控制 | `source_platform` / `etl_time` / `dt` | VARCHAR / TIMESTAMP | 平台标识 + 日期分区 |

> 设计要点：`source_platform` 区分 gitee/github；`dt` 为日期分区字段，`ods_loader.py` 幂等写入时先 `DELETE FROM ... WHERE dt = %s` 再插入，避免重复执行产生脏数据。

### 3.2 DWD 层 —— 星型模型（3 维度 + 1 事实）

```
              ┌──────────────┐
              │   dim_date   │
              │  (日期维度)   │
              └──────┬───────┘
                     │ snapshot_date
  ┌──────────┐  ┌────┴──────────┐  ┌──────────┐
  │dim_project│──│fact_repo_stats│──│ dim_org  │
  │ (项目维度) │  │ (日快照事实)   │  │(组织维度) │
  └──────────┘  └───────────────┘  └──────────┘
```

| 表 | 类型 | 主键 | 说明 |
|----|------|------|------|
| `dim_project` | 项目维度 | `project_id` | SCD Type1，`ON DUPLICATE KEY UPDATE` 覆盖更新 |
| `dim_org` | 组织维度 | `(org_name, source_platform)` | 联合主键解决同名组织跨平台冲突 |
| `dim_date` | 日期维度 | `date_id` | 2010-01-01 ~ 2030-12-31，含年/季/月/周/周末 |
| `fact_repo_stats` | 事实表 | `snapshot_id`（自增） | 每仓库每天一条快照，保留历史趋势 |

> 设计要点：`fact_repo_stats` 采用**日快照机制**——每天对每个仓库 INSERT 一条新记录（`snapshot_date` 区分），从而保留 Star/Fork/Issue 的历史变化，为后续增量分析提供基础。这也是 DWS 层能做增量计算的前提。

### 3.3 DWS 层 —— 日粒度汇总（4 张表）

| 表 | 粒度 | 核心字段 | 增量字段 |
|----|------|---------|---------|
| `dws_project_daily` | 项目 × 日 | `total_cum_stars` / `total_cum_forks` | `curr_day_new_stars` / `curr_day_new_forks` / `curr_day_new_issues` |
| `dws_language_daily` | 语言 × 日 | `repo_count` / `total_stars` / `avg_stars` | 无（纯聚合） |
| `dws_org_daily` | 组织 × 日 | `repo_count` / `total_stars` | `curr_day_new_repos` |
| `dws_platform_daily` | 平台 × 日 | `repo_count` / `total_stars` / `active_projects` | 无（纯聚合） |

> 增量字段（`curr_day_new_*`）是本层的关键产出，由"两步法"计算（见 4.2），供 ADS 层的排名、趋势直接引用。

### 3.4 ADS 层 —— 应用宽表（5 张表）

| 表 | 对应大屏位置 | 关键字段 |
|----|------------|---------|
| `ads_overview` | 顶部 4 个数字卡片 | 总仓库 / 总 Star / 总 Fork / 组织数 / 平台分布 |
| `ads_project_ranking` | Star 排名 TOP20 柱状图 | 排名 / 项目名 / Star / 日增长 `star_growth` |
| `ads_language_dist` | 语言分布环形图 | 语言 / 仓库数 / Star / 占比 `pct_of_total` |
| `ads_monthly_trend` | 月度趋势面积图 | 月份 / 新增仓库 / 活跃仓库 / 新增 Star / 累计 Star |
| `ads_org_compare` | 组织对比横向柱状图 | 组织 / Star / 平均 Star / 活跃率 |

## 4. ETL 设计

### 4.1 ODS → DWD（星型模型加载）

脚本：`scripts/etl_ods_to_dwd.py`

```sql
-- ① dim_project：SCD Type1 覆盖更新（同一仓库多次采集只保留最新属性）
INSERT INTO dim_project (...) SELECT ... FROM ods_repos_raw WHERE dt = %s
ON DUPLICATE KEY UPDATE project_name = VALUES(project_name), ...;

-- ② dim_org：INSERT IGNORE 幂等插入（联合主键去重）
INSERT IGNORE INTO dim_org (org_name, source_platform)
SELECT DISTINCT org, source_platform FROM ods_repos_raw WHERE dt = %s;

-- ③ fact_repo_stats：日快照 INSERT（每天新增一行，保留历史）
INSERT INTO fact_repo_stats (..., snapshot_date, ...)
SELECT ..., %s AS snapshot_date FROM ods_repos_raw WHERE dt = %s;
```

**注意**：该脚本通过 `SELECT MAX(dt) FROM ods_repos_raw` 只处理**最新一个分区**，是"按最新日期增量"而非"全量回补"（见 6.1 问题 2）。

### 4.2 DWD → DWS（两步法 —— 为什么不用 LAG）⭐

脚本：`scripts/etl_dwd_to_dws.py`

这是本数仓最核心、也是踩过坑的一处设计。最初的实现是在 `INSERT` 的子查询里用 `LAG()` 窗口函数直接算增量：

```sql
-- ❌ 初版方案（有缺陷）
INSERT INTO dws_project_daily (..., curr_day_new_stars)
SELECT ...,
    stars_count - LAG(stars_count, 1, 0) OVER (PARTITION BY project_id ORDER BY snapshot_date)
FROM fact_repo_stats ...;
```

**为什么这个方案不对**：`LAG()` 写在 `INSERT ... SELECT` 的子查询里时，子查询只能看到**本次从 `fact_repo_stats` 聚合出来的行**，看不到 `dws_project_daily` 表里**已经存在的历史行**。如果源表某天只有一天的数据（本项目早期就是这种情况），窗口内只有一行，`LAG()` 恒返回默认值 `0`，于是**增量恒为 0**。

**改进后的"两步法"**——把"写累计值"和"算增量"拆成两步：

```sql
-- 第 1 步：INSERT 只写入累计/基数值，不做增量计算
INSERT INTO dws_project_daily (project_id, snapshot_date, total_cum_stars, total_cum_forks)
SELECT project_id, snapshot_date, MAX(stars_count), MAX(forks_count)
FROM fact_repo_stats GROUP BY project_id, snapshot_date
ON DUPLICATE KEY UPDATE total_cum_stars = VALUES(total_cum_stars), ...;

-- 第 2 步：UPDATE 用表自身的历史行算增量（今天累计 - 昨天累计）
UPDATE dws_project_daily t
LEFT JOIN dws_project_daily y
    ON t.project_id = y.project_id
    AND y.snapshot_date = DATE_SUB(t.snapshot_date, INTERVAL 1 DAY)
SET t.curr_day_new_stars =
    t.total_cum_stars - COALESCE(y.total_cum_stars, t.total_cum_stars);
```

**两步法的优点**：
1. 增量从 **DWS 表自己的历史行**计算，无论源表 `fact_repo_stats` 里有多少天的数据，都能正确算出 `delta = 今天累计 - 昨天累计`；
2. 逻辑清晰：INSERT 管"有多少"，UPDATE 管"涨了多少"，职责分离、可单独重跑；
3. 避免了在长 SQL 里嵌套窗口函数导致的性能和可读性问题。

**仍然存在的边界问题**（见 6.1 问题 3）：`DATE_SUB(..., INTERVAL 1 DAY)` 假设快照是**连续每日**的，一旦某天缺失（本项目 8/10 缺采），`LEFT JOIN` 匹配不到"昨天"，`COALESCE` 兜底成"今天自身"，增量退化为 0。

### 4.3 DWS → ADS（应用宽表）

脚本：`scripts/etl_dws_to_ads.py`

- **ADS-1 概览**：`dim_project LEFT JOIN fact_repo_stats`（最新快照）一次取全貌，`COUNT(DISTINCT)` 统计仓库/组织数。
- **ADS-2 排名**：`ROW_NUMBER() OVER (ORDER BY total_cum_stars DESC)` 生成 1-20 名；`star_growth` 直接取 `dws_project_daily.curr_day_new_stars`（不再在事实表里二次算 LAG）。
- **ADS-3 语言分布**：`SUM(total_stars) OVER()` 窗口函数算占比。
- **ADS-4 月度趋势**：从 ODS 的 `created_at` 提取月份生成完整月份序列，再 LEFT JOIN 组织层/项目层/平台层的月度聚合。
- **ADS-5 组织对比**：`source_platform` 从 `dim_org` JOIN 获取，避免硬编码。

脚本 `etl_dws_to_ads.py` 顶部记录了对计划脚本的 **5 处修正**（取 `MAX(snapshot_date)` 而非 `now()`、star_growth 改用 DWS 增量、月度趋势列名/累计口径修复等），是本项目"边做边校正口径"的真实记录。

## 6. 已知问题与改进方向

### 6.1 数据链路问题

**P1 —— 增量指标 `curr_day_new_stars` / `star_growth` 恒为 0**

三层原因叠加：
1. **采集非真正"增量"**：`collector.py` 每次是全量重抓当前值，经 `cleaner.py` 按 `(repo_id, source_platform)` 去重后，同一仓库在各快照日的 `stars_count` 完全相同（实测 tensorflow 四个快照日均为 196,805）。因此单仓库的"今日-昨日"本来就接近 0；总 Star 变化主要来自**新增仓库**而非存量仓库涨星。
2. **缺采日破坏连续性**（P3）：8/10 未采集，`DATE_SUB(INTERVAL 1 DAY)` 匹配不到"昨天"，`COALESCE` 兜底后 `今天-今天=0`。
3. **Gitee 采集失败**（P4）：8/08 起 Gitee 返回空，双平台中一半数据源缺失，进一步摊薄增量。

> 改进：① 增量口径改为"首日出现即计入新增，后续日按 `累计-昨日累计`"并显式处理非连续日期（用 `LAG` 按 `PARTITION BY project_id ORDER BY snapshot_date` 而非 `DATE_SUB`）；② 排查 Gitee Token 是否过期/被限流；③ 若论文强调"日增长"指标，需先修复采集连续性，否则该指标无展示价值。

**P2 —— 首批次（8/05，12,175 行）未灌入 DWD**

`etl_ods_to_dwd.py` 用 `SELECT MAX(dt)` 只处理最新分区，导致最早一批永远不参与 DWD 建模。当前 `fact_repo_stats` 缺 8/05 快照日。

> 改进：ETL 改为"按 dt 遍历所有未处理分区"或"全量重建 + 幂等覆盖"，保证历史批次不丢。

**P3 —— 快照不连续（缺 8/10）**

事实表快照日为 8/07、8/08、8/09、8/11，中间缺 8/10，说明 8/10 当天未跑采集或采集后未入库。

> 改进：接入调度（如 cron / Windows 计划任务）保证每日固定采集，避免手工遗漏。

**P4 —— Gitee 采集 8/08 起返回空**

`data/raw/gitee_repos_20260808.json` 等文件仅 2 字节（空数组），GitHub 正常。可能原因：Gitee Token 失效、触发限流（403）、或组织 API 路径变更。

> 改进：① 校验 `.env` 中 `GITEE_TOKEN` 有效性；② 采集脚本增加"空结果告警"（返回 0 条时记录 WARN 而非静默成功）。

### 6.2 数据质量问题

- **语言"未标注"占比过高**：12,213 个仓库中 6,429 个无语言标签（52.6%），是 `ads_language_dist` 中最大分类，会稀释语言分布分析的准确性。
  > 改进：对"未标注"仓库尝试从 README/文件后缀推断语言，或在清洗阶段二次标注。
- **跨平台同名组织归属**：`dim_org` 联合主键 `(org_name, source_platform)` 已解决主键冲突，但 `ads_org_compare` 里 `source_platform` 仍可能因 JOIN 只取到首次入库平台，跨平台组织的平台归属仅供参考（`04_create_ads.sql` 注释已注明）。
- **历史口径差异**：第 1 周回顾中的"24,350 仓库 / GitHub 7.87M Star"为**原始未过滤/行数口径**，与本文件"12,213 仓库 / 3.99M Star"的**去重后口径**不同。写论文时需统一口径，建议以本文件 ADS 层口径为准。

### 6.3 运维问题

- **MySQL 服务非开机自启**：验证时发现 `MySQL80` 服务处于 STOPPED 状态（需手动 `net start`）。建议设为自动启动，并在 Flask 启动时做 DB 健康检查（已具备 `/api/health`）。
- **前端依赖 CDN**：`index.html` 等页面通过 jsdelivr CDN 加载 ECharts，离线/内网环境无法渲染。若答辩现场无外网，需把 `echarts.min.js` 下载到 `frontend/` 本地引用。
