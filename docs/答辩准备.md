> 项目：信创开源生态数据分析系统
> 建议演练时间：开场 1 分钟 + 演示 3 分钟 + 问答 5 分钟

---

## 一、开场白（1 分钟，背熟）

「各位老师好，我的毕业设计题目是**信创开源生态数据分析系统**。

信创产业是国家战略方向，开源软件是信创生态的核心载体。我的系统围绕『**信创开源生态现在发展得怎么样**』这个问题，做了三件事：

**第一，采集**——从 Gitee 和 GitHub 两个平台，采集 openEuler、龙蜥、OpenHarmony、昇思、openGauss 等 12 个信创主流开源组织的数据；

**第二，建模**——按数据仓库规范，构建了 ODS → DWD → DWS → ADS 四层模型，把原始数据加工成可直接分析的应用指标；

**第三，呈现**——用 Flask 提供 API，ECharts 做大屏可视化，把生态规模、项目排名、语言分布、组织活跃度、月度趋势直观呈现出来，并实现了基于 JWT 的三级权限管理和操作审计。

整个系统用 Docker Compose 一键部署，33 个测试用例全部通过。」

## 四、高频问答（15 道，附参考回答）

### Q1：为什么选这个题目？
信创是国家战略，但信创开源生态的规模、活跃度、趋势缺乏直观数据支撑。我的系统用数据说话，把分散在 Gitee/GitHub 的生态数据汇聚、建模、可视化，为生态观察和决策提供依据。

### Q2：数据仓库为什么要分四层？
分层是为了**解耦与复用**。ODS 贴源层保留原始数据、方便回溯；DWD 明细层做清洗和维度建模（星型模型）；DWS 汇总层做轻度聚合；ADS 应用层直接面向报表和 API。每一层职责单一，上游变更不影响下游，指标口径统一。

### Q3：四层各自存了什么？
- ODS：`ods_repos_raw`（原始仓库，Gitee+GitHub 合并）
- DWD：`dim_project`/`dim_org`/`dim_date` + `fact_repo_stats`（星型模型，仓库日快照事实表）
- DWS：`dws_project_daily`/`dws_org_daily`/`dws_language_daily`/`dws_platform_daily`
- ADS：`ads_overview`/`ads_project_ranking`/`ads_language_dist`/`ads_monthly_trend`/`ads_org_compare`

### Q4：为什么用 MySQL，不用 Hadoop/Hive/ClickHouse？
两个原因：**一是信创适配**——MySQL 在国产化环境（openEuler 等）成熟稳定、部署简单；**二是数据规模**——核心数据十几万行，MySQL 完全能支撑，引入大数据组件是过度设计。数据量上去了再换列式存储也不迟。

### Q5：ETL 流程是怎样的？
`collector.py`（requests 采集 API）→ `cleaner.py`（清洗）→ `ods_loader.py`（入库 ODS）→ `etl_ods_to_dwd.py` → `etl_dwd_to_dws.py` → `etl_dws_to_ads.py`，外加 `fill_dim_date.py`（日期维度预填充）。全程用 pandas + pymysql，可重复执行（`ON DUPLICATE KEY UPDATE` 幂等）。

### Q6：JWT 鉴权原理？
登录成功后服务端用密钥签发 token（payload 含 user_id/username/role），前端存到 localStorage，之后每次请求放 `Authorization: Bearer <token>` 头。后端用装饰器 `@login_required` 解码校验，`@admin_required` 再校验角色。密码本身用 scrypt 哈希存储，不存明文。

### Q7：三级权限怎么实现的？
- 公开接口（overview/ranking 等）：无需登录
- 需登录接口（me/export/change-password）：`@login_required`
- 管理员接口（users/logs）：`@login_required` + `@admin_required`
未登录返回 401，普通用户访问管理接口返回 403，都有测试用例覆盖。

### Q8：怎么防 SQL 注入？
全部用 pymysql 参数化查询 `cursor.execute(sql, params)`，占位符 `%s`，用户输入不会拼进 SQL 字符串。动态字段（如用户更新）的列名是代码里写死的白名单，值走参数。

### Q9：CSV 导出中文乱码怎么解决的？
在文件头加 UTF-8 **BOM**（`﻿`），Excel 就能正确识别编码；`Content-Disposition` 指定附件名。这是 Excel 对无 BOM UTF-8 的兼容性问题。

### Q10：Docker 部署架构？
两个服务：`mysql:8.0`（数据卷持久化 + 首次启动自动导入 `db/xinchuang_dw.sql` 建库建表灌数据）+ `web`（python:3.11-slim 构建的 Flask 镜像）。web 通过 `depends_on` + 健康检查等 MySQL 就绪后再启动，通过服务名 `mysql` 连接。`.env` 走环境变量注入，不进镜像。

### Q11：数据从哪来？API 限速怎么办？
Gitee/GitHub 官方 API。GitHub 匿名访问 60 次/小时，所以配置了 Token 提升额度；请求间隔 `REQUEST_INTERVAL=0.5s` 控制频率，单页 100 条分页拉取。

### Q12：数据质量怎么保证？
采集后清洗（`cleaner.py`）：去重、字段规范化（时区格式统一、缺失值处理）、平台字段标注；维度建模用 SCD Type1 覆盖更新；`source_platform` 字段区分 gitee/github 避免组织重名冲突（联合主键）。

### Q13：测试怎么做的？
黑盒测试为主，33 个用例分三类：功能测试 21 个、权限测试 5 个、边界异常 7 个，全部通过。覆盖登录、各接口取数、增删改查、三级权限拦截、非法输入校验（非法角色/重名/自删/弱密码等）。

### Q14：遇到最大的难点是什么？
两个：**一是跨平台数据口径统一**——Gitee 和 GitHub 的字段、时区格式、组织命名不一致，需要统一表结构和清洗规则；**二是 ETL 增量计算**——Star 日增量最初想用 LAG 窗口函数在单表里算，发现跨天数据不全，改成 DWS 层「两步法」先算当日累计再求差，才得到正确的 `star_growth`。

### Q15：系统还有什么不足/改进方向？
诚实说三点：① `/api/repos` 单次返回 2.6MB，公网下应做服务端分页（测试报告已记为遗留优化项）；② JWT 目前未设过期时间，应加 `exp` 实现令牌时效；③ 月度趋势需要积累更多月份数据才更有分析价值，目前只有短期快照。

## 五、可能的追问（刁难版，附应对思路）

1. **「你这数据是爬虫吧，合规吗？」** → 用的是官方公开 API，遵守限速，仅采集公开仓库元数据（Star/Fork/语言等），不采集任何私有或个人隐私数据。
2. **「数仓分层是不是过度设计？」** → 分层换来的是指标口径统一和可维护性，对一个要做多维分析的系统是必要投资；且我每层都有真实数据落库，不是空架子。
3. **「Star 数能代表生态繁荣吗？」** → 只能代表一个维度（关注度），所以我同时采集了 Fork、活跃度、新增仓库数、月度趋势等多维指标，避免单一指标误判。
4. **「为什么前端不用 Vue/React？」** → 需求是数据大屏，核心在图表和快速迭代，原生 JS + ECharts 足够且无构建负担；论文重点在后端数仓与数据链路，不堆前端框架。
5. **「你自己写了几行代码？」** → 如实回答：后端 app.py 约 550 行、ETL 脚本约 800 行、前端 15 个页面，均为独立完成（可当场演示 git 提交记录）。
