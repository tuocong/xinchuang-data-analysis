## 第一章　研究背景与意义

### 1.1 研究背景

信息技术应用创新（简称"信创"）是我国在信息技术领域实施自主可控战略的重要部署，其核心目标是在关键软硬件领域实现从底层芯片、操作系统、数据库、中间件到上层应用的全面国产替代。近年来，随着国家政策持续推动与产业生态逐步成熟，信创产业已从早期的试点验证阶段进入规模化落地阶段，形成了覆盖 CPU（鲲鹏、飞腾）、操作系统（openEuler、统信 UOS、麒麟）、数据库（openGauss、达梦）、人工智能框架（MindSpore）等环节的完整产品谱系。

开源是信创产业落地与生态繁荣的核心方式。国产信创基础软件几乎无一例外地选择以开源社区的形式运作：操作系统领域的 openEuler、龙蜥（Anolis OS）、开放麒麟，人工智能框架领域的 MindSpore、PaddlePaddle，数据库领域的 openGauss，以及物联网操作系统 OpenHarmony、云原生项目 KubeEdge、Karmada 等，均依托开源社区吸引全球开发者、加速技术迭代。可以说，衡量信创开源生态的健康程度——项目的关注度、社区活跃度、技术栈构成与增长趋势——直接反映了信创产业的真实发展水平。

然而，信创开源项目分散在 **Gitee 与 GitHub 两个异构平台**之上：以 openEuler、MindSpore、openGauss、龙蜥、深度、开放麒麟、鲲鹏为代表的项目主要托管于国产平台 Gitee，而以 PaddlePaddle、KubeEdge、Karmada、TiDB、Prometheus 为代表的国际化项目主要托管于 GitHub。两个平台的 API 规范、数据字段、限流策略各不相同，导致信创开源生态的全局数据长期处于"分散、异构、难统一"的状态。目前业界缺乏一套能够**自动采集、清洗、统一建模、多维分析**双平台信创开源项目健康度数据的系统化方案，社区运营者与决策者难以获得实时的、跨平台的生态全景视图。

针对上述问题，本课题设计并实现"信创开源生态数据分析系统"。系统以 Gitee 与 GitHub 双平台为数据源，采用 Python 自动采集指定信创组织与关键词关联的公开仓库数据，经清洗后按 **ODS→DWD→DWS→ADS 四层数据仓库**架构建模，最终以可视化数据大屏的形式，呈现信创开源项目在 Star 增长趋势、社区活跃度、技术语言分布、组织对比等维度的健康度指标。系统实际采集并建模了 12 个 Gitee 信创组织与 20 个 GitHub 国际组织的 **12,213 个仓库、2,067 个组织、399 万 Star**，数据具备真实性与代表性。

### 1.2 国内外研究现状

开源软件的数据化分析在国内外已有一定积累，但针对"信创 + 双平台统一"的专门化研究仍属空白。

**国外方面**，开源数据分析主要依托全球最大的代码托管平台 GitHub。谷歌主导的 GitHub Archive（GHArchive）与 BigQuery 公开数据集提供了 GitHub 全量事件流水，是学术界与工业界研究开源社区行为的主要数据源；PingCAP 开源的 OSS Insight 提供了面向 GitHub 的可视化分析工具；Linux 基金会旗下 CHAOSS 项目则定义了开源社区健康度的指标体系。然而，这些平台与工具**仅覆盖 GitHub 单一平台**，无法触及以 Gitee 为核心的国内信创开源生态。

**国内方面**，Gitee 开放了 Open API v5 接口，为第三方系统获取仓库与组织数据提供了基础；开源社每年发布《中国开源年度报告》、中国信通院发布《开源生态白皮书》，从宏观层面刻画国内开源发展态势。但此类成果多为**周期性的手工统计或年度报告**，缺乏**自动化、近实时、双平台统一口径**的分析系统，难以支撑信创生态的日常运营与精细化决策。

综上，现有工作在"数据源单一"与"分析自动化不足"两个方面存在明显缺口：国外方案不覆盖 Gitee，国内报告缺乏系统化工具。**面向双平台（Gitee+GitHub）的统一采集 → 四层数仓建模 → 可视化大屏的端到端系统化方案，正是本课题试图填补的空白。**

### 1.3 研究意义

**理论意义**：本课题探索了异构 RESTful API 数据源的统一采集与字段归一化方法，实践了面向开源项目数据的四层数据仓库（ODS→DWD→DWS→ADS）建模，尤其是基于星型模型与"日快照事实表"的增量计算设计，为"开源生态数据分析"这一细分场景提供了可复用的建模范式。

**实践意义**：系统为信创项目管理方、开源社区运营者提供实时的项目健康度看板，支持按平台、组织、语言、时间等多维度对比分析（如 Gitee 与 GitHub 上信创项目 Star 增长的横向比较），有助于及时发现生态短板、引导资源投入。此外，系统内置的用户管理与操作日志审计能力，使其具备实际部署使用的工程完备性。

## 第二章　相关技术综述

### 2.1 数据采集技术

系统采用 Python 的 `requests` 库调用 Gitee Open API v5 与 GitHub REST API v3 两类异构接口。为应对两平台差异，采集器采用**面向对象的继承设计**：基类 `BaseRepoCollector` 封装了 HTTP 会话复用（`requests.Session`）、分页采集、JSON 落盘以及**指数退避重试**（请求失败按 `2^attempt` 秒退避重试，最大重试次数 3 次）等通用逻辑，用于应对 403 限流等异常；子类 `GiteeCollector` 与 `GitHubCollector` 分别实现各自的 `_normalize()` 字段标准化方法，将 Gitee 的 22 个字段与 GitHub 的 28 个字段**统一归一化为 21 个公共字段**（Gitee 缺失的 topics、license、homepage、archived 等字段补默认值）。采集策略上，采用"组织列表遍历 + 关键词搜索补充"双阶段方式，关键词包括 `xinchuang`、`信创`、`kunpeng`、`ascend`、`harmonyos`、`openHarmony`、`openEuler` 等 7 个，并以 `(repo_id, source_platform)` 组合键去重。

### 2.2 数据清洗技术

数据清洗基于 Pandas 完成，实现为一条七步处理管道：① 字段补全（Gitee 缺失字段补默认值）；② 按 `(repo_id, source_platform)` 去重（`drop_duplicates`）；③ 空描述填充为"无"（`fillna`）；④ 无效仓库过滤（Gitee 已迁移仓库、GitHub 已归档仓库）；⑤ 超长描述清理（超过 15000 字符视为垃圾数据删除）；⑥ 语言为空标注为"未标注"；⑦ topics 列表转换为逗号分隔字符串。清洗完成后输出平台对比、组织分布、Star 分布区间、语言分布、时间趋势等多维统计报告，为后续建模提供质量可控的明细数据。

### 2.3 数据仓库技术

系统采用经典的数据仓库**四层分层架构**：**ODS**（贴源层，与原始 API 数据 1:1 对应，按 `dt` 日期分区，幂等写入）；**DWD**（明细层，采用**星型模型**——`dim_project`、`dim_org`、`dim_date` 三个维度表围绕 `fact_repo_stats` 事实表，维度表采用 SCD Type 1 缓慢变化维的覆盖更新，事实表采用**日快照机制**每天新增一条记录以保留历史趋势）；**DWS**（汇总层，按项目/语言/组织/平台四个粒度做日聚合，并计算"当日新增 Star/Fork/仓库数"等增量字段）；**ADS**（应用层，构建 `ads_overview`、`ads_project_ranking`、`ads_language_dist`、`ads_monthly_trend`、`ads_org_compare` 五张面向前端的宽表，避免复杂 JOIN）。

在增量计算上，本课题实践并改进了一种**"两步法"**：先将累计值 INSERT 入 DWS 表，再通过 UPDATE 结合 `LEFT JOIN` 表自身"昨日"行计算增量（`今日累计 - 昨日累计`），规避了在 `INSERT...SELECT` 子查询中直接使用 `LAG()` 窗口函数时"窗口内仅有一行导致增量恒为 0"的缺陷。排名使用 `ROW_NUMBER()` 窗口函数，占比使用 `SUM() OVER()` 窗口函数。

### 2.4 后端开发技术

后端采用 Flask 轻量级 Web 框架，配合 Flask-CORS 处理跨域、PyMySQL 连接 MySQL 数据库。接口层实现统一 JSON 响应规范（`{"code": 0, "data": ...}`）与自定义序列化（日期、Decimal 类型）。在安全与权限上，系统基于 PyJWT 实现 **JWT 无状态认证**（HS256 算法），密码采用 `werkzeug` 的 PBKDF2 加盐哈希存储，并实现"公开 / 需登录 / 仅管理员"的**三级权限模型**——通过 `@login_required` 与 `@admin_required` 装饰器叠加实现"先登录、后鉴权"。系统共提供 18 个 RESTful 接口，涵盖概览、排名、语言分布、趋势、组织对比、组织钻取、仓库明细等分析接口，以及登录、用户管理、操作日志、修改密码、个人统计、数据导出等管理与审计接口；关键操作均写入 `sys_log` 操作日志，实现全程可审计。

### 2.5 前端可视化技术

前端采用**纯 HTML5 + CSS3 + 原生 JavaScript + Apache ECharts 5** 实现，无需前端构建工具与框架，由 Flask 统一托管静态页面，部署轻量、依赖极少。可视化方面，使用 ECharts 绘制柱状图、饼图/环形图、折线图/面积图、横向柱状图、雷达图等多种图表；界面采用统一的**暗色主题与设计令牌（Design Tokens）**，通过 CSS 变量统一管理页面底色、卡片底色与系列色板，保证 14 个页面视觉风格一致。前端通过封装的 `authFetch()` 统一附加 `Authorization: Bearer <token>` 请求头，并在接口返回 401 时自动清除本地令牌跳转登录页，实现会话过期的统一拦截。

### 2.6 部署技术

系统拟采用 Docker 容器化部署，通过 Dockerfile 构建后端镜像，并以 docker-compose 编排 MySQL、Flask 等服务，实现"一键启动"的标准化部署，降低环境依赖与迁移成本。

## 第三章　系统分析与设计

### 3.1 需求分析

#### 3.1.1 功能需求

系统围绕"信创开源生态数据分析"这一目标，划分为数据链路、分析展示、系统管理三大类功能。经需求整理，确定如下功能需求：

| 编号 | 功能 | 需求描述 |
|------|------|---------|
| F1 | 双平台数据采集 | 自动采集 Gitee/GitHub 指定组织公开仓库，支持"组织遍历 + 关键词搜索"两种模式，具备分页与失败重试能力 |
| F2 | 数据清洗 | 对原始数据按（repo_id+平台）去重、空值填充、无效仓库过滤（已迁移/已归档）、双平台字段归一化 |
| F3 | 数仓分层建模 | 按 ODS→DWD→DWS→ADS 四层建模，DWD 采用星型模型，事实表日快照保留历史趋势 |
| F4 | 多维统计分析 | 支持按平台/组织/语言/时间维度的 Star、Fork、Issue 统计，TOP20 排名、日增长量与月度趋势追踪 |
| F5 | 可视化大屏 | 数据大屏 + 排名/语言/趋势/组织对比/组织钻取/仓库对比/筛选分析等分析页，多图表联动 |
| F6 | 用户认证与管理 | 基于 JWT 的登录认证、三级权限（公开/需登录/仅管理员）、用户增删改查 |
| F7 | 数据管理与导出 | 仓库明细的分页浏览、关键字搜索、CSV 导出 |
| F8 | 日志审计 | 对登录、导出、用户管理等关键操作记录日志，支持管理员查询 |
| F9 | 个人中心 | 个人信息维护、个人操作统计、修改密码 |

#### 3.1.2 非功能需求

- **数据幂等性**：ODS 层按 `dt` 日期分区，重复执行加载时先删除当日分区再写入，避免产生脏数据；
- **安全性**：密码 PBKDF2 加盐哈希存储、JWT 无状态认证、接口三级权限校验、关键操作全程审计；
- **可用性**：统一 JSON 响应规范、健康检查接口（`/api/health`）用于探测数据库连通性；
- **可维护性**：采集/清洗/ETL 各环节脚本化、分层解耦，便于独立重跑与扩展。

### 3.2 系统整体架构

系统采用"采集 → 清洗 → 入仓 → 建模 → 服务 → 展示"的纵向分层架构：

```
┌──────────────┐   ┌──────────────┐
│  Gitee API   │   │  GitHub API  │   ① 数据源层
└──────┬───────┘   └──────┬───────┘
       └───────┬──────────┘
               │ collector.py（采集）
               ▼
      ┌────────────────────┐
      │ data/raw/*.json    │          ② 原始数据落盘层
      └─────────┬──────────┘
                │ cleaner.py（Pandas 清洗）
                ▼
      ┌────────────────────┐
      │ data/cleaned/*.json│          ③ 清洗后数据层
      └─────────┬──────────┘
                │ ods_loader.py（入库）
                ▼
┌──────────────────────────────────────┐
│          MySQL（xinchuang_dw）        │
│  ODS  ods_repos_raw      （贴源层）    │ ④ 数据存储层
│  DWD  dim_* + fact_repo_stats（星型）  │
│  DWS  dws_*_daily        （汇总）      │
│  ADS  ads_*              （应用）      │
│  sys_user / sys_log      （系统）      │
└───────────────┬──────────────────────┘
                │ Flask API（18 个接口）
                ▼
      ┌────────────────────┐
      │ 纯 HTML + ECharts   │          ⑤ 展示层
      │ 数据大屏（14 页面）  │
      └────────────────────┘
```

各层职责清晰：数据源层对接两类异构 API；落盘与清洗层完成数据质量治理；存储层以四层数仓承载"贴源—明细—汇总—应用"的逐层加工；服务层以 RESTful API 对外提供统一数据访问；展示层以 ECharts 呈现可视化结果。

### 3.3 数据库设计

系统数据库共 **16 张表**，其中数据仓库 14 张、系统管理 2 张。

#### 3.3.1 ODS 层（贴源层）

`ods_repos_raw` 表与采集器归一化后的 JSON 字段 1:1 对应，共 **21 个字段**：基础标识（repo_id、org、name、full_name、description）、核心指标（stars_count、forks_count、watchers_count、open_issues_count）、仓库属性（language、default_branch、html_url）、GitHub 特有字段（topics、license_type、homepage、archived，Gitee 填默认值）、时间字段（created_at、updated_at、pushed_at）与 ETL 控制字段（source_platform、etl_time、dt）。`source_platform` 区分 gitee/github，`dt` 为日期分区字段。

#### 3.3.2 DWD 层（明细层 —— 星型模型）

DWD 层采用**星型模型**，由 3 个维度表 + 1 个事实表构成：

```
              ┌──────────────┐
              │   dim_date   │（日期维度）
              └──────┬───────┘
                     │ snapshot_date
  ┌──────────┐  ┌────┴──────────┐  ┌──────────┐
  │dim_project│──│fact_repo_stats│──│ dim_org  │
  │ (项目维度) │  │ (日快照事实)   │  │(组织维度) │
  └──────────┘  └───────────────┘  └──────────┘
```

- `dim_project`（项目维度，主键 project_id）：采用 SCD Type 1 覆盖更新；
- `dim_org`（组织维度，联合主键 org_name + source_platform）：解决同名组织跨平台冲突；
- `dim_date`（日期维度，主键 date_id）：2010-01-01 至 2030-12-31，含年/季/月/周/是否周末；
- `fact_repo_stats`（事实表，主键 snapshot_id 自增）：每仓库每天一条快照，保留 Star/Fork/Issue 历史变化。

#### 3.3.3 DWS 层（汇总层 —— 日粒度聚合）

| 表 | 粒度 | 核心字段 | 增量字段 |
|----|------|---------|---------|
| `dws_project_daily` | 项目×日 | total_cum_stars / total_cum_forks | curr_day_new_stars / new_forks / new_issues |
| `dws_language_daily` | 语言×日 | repo_count / total_stars / avg_stars | 无（纯聚合） |
| `dws_org_daily` | 组织×日 | repo_count / total_stars | curr_day_new_repos |
| `dws_platform_daily` | 平台×日 | repo_count / total_stars / active_projects | 无（纯聚合） |

增量字段（curr_day_new_*）是本层关键产出，供 ADS 层排名、趋势直接引用。

#### 3.3.4 ADS 层（应用层 —— 对接前端）

| 表 | 对应展示位置 | 关键字段 |
|----|------------|---------|
| `ads_overview` | 大屏顶部数字卡片 | 总仓库 / 总 Star / 总 Fork / 组织数 / 平台分布 |
| `ads_project_ranking` | 排名柱状图 | rank_num / project_name / stars_count / star_growth |
| `ads_language_dist` | 语言环形图 | language / repo_count / total_stars / pct_of_total |
| `ads_monthly_trend` | 趋势面积图 | month / new_repos / active_repos / new_stars / cumulative_stars |
| `ads_org_compare` | 组织对比横向柱状图 | org_name / repo_count / total_stars / active_rate |

#### 3.3.5 系统管理表

`sys_user`（用户表，含 username、password_hash、role、status、create_time）与 `sys_log`（操作日志表，含 username、action、detail、ip、create_time），共同支撑用户认证与操作审计。

### 3.4 数据采集模块设计

采集器采用**面向对象继承**设计：基类 `BaseRepoCollector` 封装 HTTP 会话复用、分页采集、JSON 落盘与**指数退避重试**（失败按 2^attempt 秒退避，最多重试 3 次）；子类 `GiteeCollector`、`GitHubCollector` 分别实现 `_normalize()` 字段标准化，将 Gitee 22 字段、GitHub 28 字段统一为 21 字段。采集分两阶段：① 按组织遍历（自动分页）；② 按关键词搜索补充（7 个关键词，每个最多 5 页 × 100 条），最终以 `(repo_id, source_platform)` 去重。

### 3.5 数据清洗模块设计

清洗基于 Pandas 实现为七步管道：字段补全 → 去重 → 空描述填充 → 无效仓库过滤（Gitee 已迁移 / GitHub 已归档）→ 超长描述清理 → 语言空值标注 → topics 列表转字符串。清洗后输出平台对比、组织分布、Star 区间、语言分布、时间趋势等多维统计报告。

### 3.6 数据仓库建模与 ETL 设计

四层 ETL 的关键设计点：

- **ODS → DWD**：维度表 SCD Type 1 覆盖更新（`INSERT ... ON DUPLICATE KEY UPDATE`），组织维度 `INSERT IGNORE` 幂等插入，事实表日快照 INSERT；
- **DWD → DWS**：采用**"两步法"增量计算**——第 1 步 INSERT 写入累计/基数值，第 2 步 UPDATE 通过 `LEFT JOIN` 表自身"昨日"行计算增量（今日累计 − 昨日累计），规避了在子查询中使用 `LAG()` 时"窗口仅一行导致增量恒为 0"的缺陷；
- **DWS → ADS**：排名用 `ROW_NUMBER() OVER (ORDER BY stars_count DESC)`，占比用 `SUM() OVER()`，月度趋势从 ODS `created_at` 提取月份生成完整序列后左连各层月度聚合。

### 3.7 后端接口设计

后端基于 Flask 提供 **18 个 RESTful 接口**，统一返回 `{"code": 0, "data": ...}`。接口按权限分三级：

| 权限分级 | 接口 | 说明 |
|---------|------|------|
| 公开 | /api/overview、/api/ranking、/api/language、/api/trend、/api/org-compare、/api/org-repos、/api/repos、/api/health、/api/login | 概览、排名、语言、趋势、组织对比/钻取、仓库明细、健康检查、登录 |
| 需登录 | /api/me、/api/my-stats、/api/export、/api/change-password | 个人信息、统计、导出、改密 |
| 仅管理员 | /api/users（GET/POST/PUT/DELETE）、/api/logs | 用户管理、日志查询 |

认证基于 JWT（HS256），密码加盐哈希存储，接口通过 `@login_required` 与 `@admin_required` 装饰器叠加实现"先登录、后鉴权"。

### 3.8 前端页面设计

前端为纯 HTML + ECharts，共 **14 个页面**，分为三类：

| 类别 | 页面 | 核心交互/图表 |
|------|------|--------------|
| 可视化分析类 | 数据大屏、项目排名、语言分布、趋势分析、组织对比、组织钻取、仓库对比、项目筛选分析 | 柱状图/饼图/折线/雷达图/可展开表格，多维联动 |
| 数据管理类 | 数据管理、用户管理、系统日志 | 表格 + 分页 + 搜索 + 模态框，CSV 导出 |
| 系统辅助类 | 登录、工作台、个人中心 | 表单、KPI 卡片、统计卡片 |

前端通过 `authFetch()` 统一附加 JWT 请求头，401 时自动跳转登录，实现会话统一拦截。
