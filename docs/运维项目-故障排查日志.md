## 故障1：Grafana 无法连接 Prometheus — `no such host`

### 现象

Grafana 数据源配置为 `http://prometheus:9090`，测试连接时报错：

```
Post "http://prometheus:9090/api/v1/query":
  dial tcp: lookup prometheus on 127.0.0.11:53: no such host
```

### 排查过程

```bash
# 第1步：确认 Prometheus 容器正常运行
docker ps | grep prometheus
# → 容器存在且运行正常，端口 9090 已暴露

# 第2步：确认 Prometheus 自身可访问
curl http://localhost:9090/api/v1/query?query=up
# → 宿主机可以访问，说明 Prometheus 本身没问题

# 第3步：确认容器网络配置
docker inspect prometheus --format '{{json .NetworkSettings.Networks}}' | python3 -m json.tool
docker inspect grafana --format '{{json .NetworkSettings.Networks}}' | python3 -m json.tool
# → prometheus 在默认网络（project_default），grafana 在 monitor-net
# → 两个容器不在同一个 Docker 网络！DNS 互不解析
```

### 根因

`docker-compose.yml` 中 Grafana 单独声明了 `networks: monitor-net`，但 Prometheus 和 Node Exporter 没有声明 networks，留在了 Compose 自动创建的默认网络（`project_default`）。

Docker 内置 DNS（`127.0.0.11:53`）只在**同一网络**内生效，跨网络无法通过容器名互相解析。

### 解决方案

给所有监控组件统一加上 `networks: monitor-net`：

```yaml
prometheus:
  networks:
    - monitor-net

node-exporter:
  networks:
    - monitor-net
```

重启后 Grafana → Data Sources → Test 通过。

### 学到的知识点

- Docker Compose 中，声明了自定义网络的容器会**脱离默认网络**
- 容器之间通过服务名互访的前提是**在同一网络内**
- 排查 DNS 问题用 `docker inspect` 看各容器的网络归属
- `docker exec <容器> ping <服务名>` 可以快速验证 DNS 是否通

## 故障2：Grafana Pressure 面板显示 "No data"

### 现象

Node Exporter Full 仪表盘（ID 1860）中，CPU/内存/磁盘/网络/运行时长面板全部正常显示，唯独 Pressure（系统压力）面板显示 "No data"。

### 排查过程

```bash
# 第1步：确认 Prometheus 能抓取到指标了吗
# 在 Prometheus Web UI 查询
node_pressure_cpu_waiting_seconds_total
# → "No datapoints found"

# 第2步：确认 node_exporter 是否暴露了 pressure 指标
curl -s http://localhost:9100/metrics | grep pressure
# 输出：
#   node_scrape_collector_success{collector="pressure"} 0
# → node_exporter 尝试采集了，但失败了（success=0）

# 第3步：确认宿主机是否支持 PSI
cat /proc/pressure/cpu
# → No such file or directory
ls /proc/pressure/
# → No such file or directory

# 第4步：确认内核版本
uname -r
# → 6.6.0-159.4.3.154.oe2403sp4.x86_64
# → 内核 6.6，理论上支持 PSI（需要 ≥ 4.20）
```

### 根因

openEuler 24.03 发行版在编译内核时**未开启 `CONFIG_PSI`**（Pressure Stall Information）。

PSI 是内核编译选项，不是运行时开关。内核版本 6.6 支持该功能，但发行版选择不编译。`/proc/pressure/` 目录不存在，node_exporter 的 pressure collector 无法读取数据，返回 `success=0`。

### 解决方案

- **无法在运行态修复**：需要重新编译内核并开启 `CONFIG_PSI=y`，超出项目范围
- **处理方式**：删除 Grafana 仪表盘中的 Pressure 面板（不影响其他监控指标）

### 学到的知识点

- `node_scrape_collector_success{collector="xxx"}` 指标可以判断某个 collector 是否采集成功（0=失败，1=成功）
- `/proc/pressure/` 需要内核编译时开启 `CONFIG_PSI`，不是高版本内核就一定有
- 排查路径：Grafana（无数据）→ Prometheus（无 metric）→ node_exporter（collector 失败）→ 宿主机（文件不存在）→ 内核（编译选项未开启）
- 不是所有问题都要修复——判断是否可修复、是否值得修复，也是运维能力

## 故障3：docker-compose.yml 网络配置最佳实践

### 经验总结

经过故障1后，整理的 docker-compose 网络规则：

| 场景 | 推荐做法 |
|------|---------|
| 所有服务需要互通 | 全加入同一个自定义网络 |
| 部分服务对外暴露 | 前端/API 不加入监控网络，监控组件单独组网 |
| 多 Compose 文件共享网络 | 使用 `external: true` 的外部网络 |
| 排查 DNS 问题 | `docker inspect` 看网络归属 → `docker exec` ping 服务名 |

### 当前项目最终配置

```
networks:
  monitor-net:      ← 自定义桥接网络
    driver: bridge

services:
  flask-app:        ← 默认网络（对外服务，不需要被监控访问）
  nginx:            ← 默认网络
  prometheus:       ← monitor-net（监控组件统一网络）
  node-exporter:    ← monitor-net
  grafana:          ← monitor-net
```
