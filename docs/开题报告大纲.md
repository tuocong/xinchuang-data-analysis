## 第一章  研究背景与意义（约1500字）

### 1.1 研究背景

**要写什么：**

- 信创（信息技术应用创新）是国家战略，涵盖国产 CPU（鲲鹏/飞腾）、操作系统（openEuler/统信UOS/麒麟）、数据库（openGauss/达梦）、中间件等全面自主替代
- 开源是信创落地的核心方式：openEuler（操作系统）、MindSpore（AI框架）、openGauss（数据库）、OpenHarmony（物联网OS）、龙蜥社区（Anolis OS）等都是通过开源社区运作
- 但这些信创开源项目分散在 Gitee 和 GitHub 两个平台：
  - Gitee：openEuler、MindSpore、openGauss、龙蜥、深度、开放麒麟等国产主导的开源项目
  - GitHub：PaddlePaddle、KubeEdge、Karmada、TiDB、Prometheus 等国际化项目
- 目前缺乏一个系统来自动采集、清洗、分析双平台的信创开源项目健康度数据（Star趋势、社区活跃度、技术语言分布）
- → 本课题要解决的就是这个问题

**用到的素材（你的项目实际数据）：**

- `project_config.py` 中配置的 12 个 Gitee 组织 + 16 个 GitHub 组织 + 7 个搜索关键词
- 实际采集到 2,038 个组织、24,350 个仓库
- 数据量说明项目有真实价值，不是假数据

### 1.2 国内外研究现状

**分三段写：**

| 层面 | 现状 | 不足 |
|------|------|------|
| 国外 | GitHub Archive、GHArchive（Google BigQuery 上的公开数据集）、OSS Insight（PingCAP 开源的 GitHub 分析工具） | 只覆盖 GitHub，不涉及 Gitee 和国内信创生态 |
| 国内 | Gitee 开放 API v5、开源社每年发布《中国开源年度报告》、中国信通院《开源生态白皮书》 | 多为手工统计/年度报告，缺乏**自动化+实时+双平台统一**的分析系统 |
| 空白点 | 双平台（Gitee+GitHub）统一采集 → 数仓四层建模 → 可视化大屏的**系统化方案** | ← 你的项目填补的空白 |

### 1.3 研究意义

- **理论意义**：探索双平台异构 API 数据源的统一采集和 ETL 处理方法，以及面向开源项目的数仓四层（ODS→DWD→DWS→ADS）建模实践
- **实践意义**：
  - 为信创项目管理方、开源社区运营者提供实时的项目健康度看板
  - 支持按平台/组织/语言/时间多维度对比分析（如 Gitee vs GitHub 信创项目 Star 增长趋势）
- **个人意义**：掌握完整的数据采集→清洗→建模→API→大屏全链路开发能力

## 第二章  相关技术综述（约1500字）

### 2.1 数据采集技术
- Python `requests` 库调用 RESTful API
- Gitee Open API v5、GitHub REST API v3
- 分页采集 + 指数退避重试机制（403 限流处理）
- 双平台字段归一化策略（Gitee 缺少 `topics`/`license`/`archived` 字段，需补默认值）
- → **素材**：`scripts/collector.py`（BaseRepoCollector → GiteeCollector / GitHubCollector 继承设计）

### 2.2 数据清洗技术
- Pandas 数据处理：`drop_duplicates()`、`fillna()`、`str.contains()`、`pd.cut()`、`groupby()`
- 清洗规则：按 `(repo_id, source_platform)` 去重、description 空值填充、Gitee 已迁移仓库过滤、GitHub 已归档仓库过滤
- 多维度统计报告：平台对比/组织分布/Star分布区间/语言分布/时间趋势
- → **素材**：`scripts/cleaner.py`

### 2.3 数据仓库技术
- 数仓四层架构：ODS（贴源层）→ DWD（明细层，星型模型）→ DWS（汇总层，日粒度聚合）→ ADS（应用层，对接前端）
- 星型模型设计：`dim_project` / `dim_org` / `dim_date` 三个维度表围绕 `fact_repo_stats` 事实表
- SCD Type 1（缓慢变化维，覆盖更新）：`INSERT ... ON DUPLICATE KEY UPDATE`
- 窗口函数：`LAG()` 计算日增长量、`ROW_NUMBER()` 排名
- 日快照机制：事实表每天 INSERT 新行保留历史（fact_repo_stats 按 snapshot_date 分区）
- → **素材**：`db/01_create_ods.sql` + 学习计划中 DWD/DWS/ADS 的 SQL 设计

### 2.4 Web 前后端技术
- 后端：Flask RESTful API（6个接口），PyMySQL 数据库连接，CORS 跨域支持
- 前端：Vue3 + Vite 构建，ECharts 数据可视化（柱状图/饼图/折线图/面积图/横向柱状图），Element Plus UI 组件库
- → **素材**：`backend/` 目录 + 学习计划中 Vue3 页面设计

### 2.5 部署技术
- Docker 容器化部署（Dockerfile + docker-compose.yml）
- docker-compose 一键编排：Flask + Nginx + MySQL 服务

### 3.3 数据库设计

#### ODS 层（贴源层）

**ods_repos_raw** — 21 个字段，与原始 API 数据 1:1 对应，保留完整信息：

| 字段分类 | 字段名 | 类型 | 说明 |
|----------|--------|------|------|
| 基础标识 | repo_id, org, name, full_name, description | BIGINT/VARCHAR/TEXT | 仓库基本属性 |
| 核心指标 | stars_count, forks_count, watchers_count, open_issues_count | INT | 关键度量 |
| 仓库属性 | language, default_branch, html_url | VARCHAR | 技术标签 |
| GitHub特有 | topics, license_type, homepage, archived | VARCHAR/TINYINT | Gitee填默认值 |
| 时间字段 | created_at, updated_at, pushed_at | VARCHAR(30) | ISO 8601格式 |
| ETL控制 | source_platform, etl_time, dt | VARCHAR/TIMESTAMP | 平台标识+分区 |

#### DWD 层（明细层 — 星型模型）

```
                ┌──────────────┐
                │  dim_date    │
                │ (日期维度)    │
                └──────┬───────┘
                       │ snapshot_date
    ┌──────────┐  ┌────┴─────────┐  ┌────────────┐
    │dim_project│──│fact_repo_stats│──│  dim_org   │
    │(项目维度)  │  │  (日快照事实)  │  │(组织维度)   │
    └──────────┘  └──────────────┘  └────────────┘
         │               │               │
    project_id      snapshot_id      org_name
    project_name    project_id (FK)   source_platform
    full_name       org_name (FK)
    description     snapshot_date (FK)
    language        stars_count
    topics          forks_count
    license_type    watchers_count
    html_url        open_issues_count
    source_platform dt / etl_time
```

- **dim_project**：仓库维度，主键 project_id，SCD Type 1 覆盖更新
- **dim_org**：组织维度，主键 org_name
- **dim_date**：标准日期维度（年/季度/月/周/是否周末）
- **fact_repo_stats**：仓库日快照事实表，每天每仓库一条记录，保留历史趋势

#### DWS 层（汇总层 — 日粒度聚合）

| 表名 | 粒度 | 核心字段 | 关键计算 |
|------|------|---------|---------|
| dws_project_daily | 项目×日 | stars/forks/issues | — |
| dws_language_daily | 语言×日 | repo_count, total_stars, avg_stars | — |
| dws_org_daily | 组织×日 | repo_count, total_stars, **new_repos** | `LAG()` 算日新增 |
| dws_platform_daily | 平台×日 | repo_count, active_projects | Gitee vs GitHub |

#### ADS 层（应用层 — 直接对接前端）

| 表名 | 对应大屏位置 | 关键数据 |
|------|------------|---------|
| ads_overview | 顶部 4 个数字卡片 | 总仓库/总Star/总Fork/组织数 |
| ads_project_ranking | TOP20 排行榜柱状图 | 排名/项目名/Star/日增长量 |
| ads_language_dist | 语言饼图/环形图 | 语言/仓库数/占比% |
| ads_monthly_trend | 月度趋势面积图 | 月份/新增仓库/新增Star/累计Star |
| ads_org_compare | 组织对比横向柱状图 | 组织/Star/活跃率 |

### 3.4 数据采集模块设计

- **架构**：`BaseRepoCollector`（父类）→ `GiteeCollector` / `GitHubCollector`（子类）

  - 子类实现：`_normalize()` 字段标准化（Gitee 22→21 字段、GitHub 28→21 字段统一）
- **采集策略**：
  - Phase 1：按组织采集（遍历组织列表，自动分页）
  - Phase 2：按关键词搜索补充（`xinchuang`/`信创`/`kunpeng`/`harmonyos` 等 7 个关键词，每个最多 5 页 × 100 条）

### 3.5 数据清洗模块设计

| 步骤 | 操作 | 方法 |
|------|------|------|
| 1 | 字段补全 | Gitee 缺失的 topics/license/homepage/archived 补默认值 |
| 2 | 去重 | `drop_duplicates(subset=["repo_id", "source_platform"])` |

| 4 | 无效过滤 | Gitee 含"迁移/migrated" → 删；GitHub archived=True → 删 |
| 5 | 超长清理 | description > 15000 字符 → 视为 spam 删除 |
| 6 | 语言标注 | language 为空 → "未标注" |
| 7 | 列表转字符串 | topics list → 逗号分隔字符串 |

## 第四章  系统实现（约2000字）

### 4.1 数据采集实现

代码结构：`collector.py` 约 260 行，类继承关系：

```
BaseRepoCollector (父类)
├── _request()       # GET + 指数退避重试
├── fetch_org_repos()  # 按组织分页采集
├── fetch_by_search()  # 按关键词搜索采集
├── save_json()        # 持久化为 JSON
└── run()              # 主流程：组织+搜索 → 去重 → 保存

GiteeCollector(BaseRepoCollector)
└── _normalize()    # 22字段 → 21字段统一格式

GitHubCollector(BaseRepoCollector)
└── _normalize()    # 28字段 → 21字段统一格式
```

关键技术点：reqests.Session() 复用连接、指数退避（2^attempt 秒）、403限流检测

### 4.2 数据清洗与 ETL 实现

清洗管道：`load_all_raw_files()` → `clean_data()`（6步）→ `print_statistics()`（8维报告）→ `save_clean_data()`

关键技术点：Pandas `pd.concat()` 合并多文件、`pd.cut()` 分段统计、`groupby()` 多维聚合

ODS 加载器：`ods_loader.py`
- 幂等性设计：`DELETE FROM ods_repos_raw WHERE dt = %s` 先删当日旧数据
- 批量写入：`executemany()` batch_size=100
- 字段归一化：`normalize_row()` 兜底函数（类型转换、超长截断、bool→0/1）

### 4.3 数仓分层 ETL 实现

**ODS → DWD**（星型模型加载）：

```sql
-- dim_project: SCD Type 1 覆盖更新
INSERT INTO dim_project (...) SELECT ... FROM ods_repos_raw WHERE dt = %s
ON DUPLICATE KEY UPDATE project_name = VALUES(project_name), ...;

-- dim_org: INSERT IGNORE 幂等插入
INSERT IGNORE INTO dim_org (org_name, source_platform) SELECT DISTINCT ...;

-- fact_repo_stats: 每日快照 INSERT
INSERT INTO fact_repo_stats (...) SELECT ..., %s AS snapshot_date FROM ods_repos_raw WHERE dt = %s;
```

**DWD → DWS**（日粒度聚合）：

```sql
-- LAG() 窗口函数计算日增长量（⭐核心）
repo_count - LAG(repo_count, 1, 0) OVER (PARTITION BY org_name ORDER BY snapshot_date) AS new_repos
```

**DWS → ADS**（应用宽表）：

```sql
-- ROW_NUMBER() 排名
INSERT INTO ads_project_ranking
SELECT ..., ROW_NUMBER() OVER (ORDER BY stars_count DESC) AS rank_num
FROM (...) ORDER BY stars_count DESC LIMIT 20;
```

### 4.4 后端 API 实现

Flask 6 路由 + PyMySQL + CORS：

| 路由 | SQL 特点 |
|------|---------|
| `/api/overview` | 聚合查询，取最新 snapshot_date |
| `/api/ranking` | `ROW_NUMBER() + LAG()` 计算排名+增长 |
| `/api/language-dist` | 分组聚合 + 占比计算 |
| `/api/monthly-trend` | `DATE_FORMAT()` 按月聚合 |
| `/api/org-compare` | 多维排序 |
| `/api/health` | 健康检查 |

## 第六章  总结与展望（约800字）

### 6.1 工作总结
- 构建了覆盖 Gitee + GitHub 双平台的信创开源项目数据采集系统
- 设计了 ODS→DWD→DWS→ADS 四层数仓模型
- 实现了 6 个 RESTful API 和 4 页面可视化大屏
- 实际采集并分析了 12 个 Gitee 组织 + 16 个 GitHub 组织，共 2,038 个组织的 24,350 个仓库

### 6.2 不足与改进
- 当前为每日全量采集，可优化为增量采集（只采集 pushed_at 变化的仓库）
- 数据采集依赖 API 限流，大规模组织（如 kubernetes、apache 的 3000+ 仓库）需要更长时间
- 分析维度可扩展：贡献者活跃度、Issue 关闭率、社区健康度指标（如 CNCF 的 CHAOSS 框架）

### 6.3 未来展望
- 接入更多数据源（GitLink、AtomGit、华为云 DevCloud）
- 引入 NLP 对仓库描述和 README 做自动分类和信创领域标签
- 实现自动化调度（每天凌晨自动采集 → 清洗 → ETL → 更新大屏）
